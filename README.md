# Практическая работа №7. Межпроцессное взаимодействие

Среда: Windows 11 + WSL2, Ubuntu 24.04, Python 3.12 (только стандартная библиотека).

## Файлы
- `common.py` - пути FIFO и сокета, безопасный вычислитель выражений (ast, без eval)
- `fifo_server.py`, `fifo_client.py` - клиент-сервер на двух именованных каналах
- `sock_server.py`, `sock_client.py`, `sock_multi_client.py` - то же на Unix-сокетах, с несколькими одновременными клиентами
- `bench_ipc.py` - передача 10^7 чисел через shared_memory, Pipe, Unix-сокет, FIFO, итоговая таблица
- `shm_sync_demo.py` - разделяемая память без синхронизации и с ней
- `pipe_demo.py` - запись в pipe без читателей и незакрытый конец записи
- `run_all.sh` - автоматический прогон всего и проверка, что ничего не осталось
- `run_all_output.txt` - вывод полного прогона

## Запуск: клиент-сервер на FIFO (два терминала)
Терминал 1:

    cd ~/os-lab7
    python3 fifo_server.py

Терминал 2 (клиенты запускаются по очереди, каждый запуск - отдельный клиент):

    cd ~/os-lab7
    python3 fifo_client.py "2+3*4" "(10-4)**2" "7/0"
    python3 fifo_client.py "100/8" "2**10"
    python3 fifo_client.py --shutdown

Сервер удаляет FIFO при выходе (по --shutdown, Ctrl+C или SIGTERM). Если сервер был убит
через kill -9, остатки можно удалить командой rm /tmp/lab7_*; новый запуск сервера
удаляет их сам.

## Запуск: клиент-сервер на Unix-сокете (два терминала)
Терминал 1:

    cd ~/os-lab7
    python3 sock_server.py --delay 0.1

Терминал 2:

    cd ~/os-lab7
    python3 sock_multi_client.py 5
    python3 sock_client.py "6*7"
    python3 sock_client.py --shutdown

sock_multi_client.py запускает 5 клиентов, каждый в отдельном процессе, и все они
отправляют запросы одновременно (барьер). Каждый клиент сверяет ответы сервера с
эталоном. Автоматический прогон всего сразу:

    ./run_all.sh

## Как устроено

### FIFO
Канал односторонний, поэтому два FIFO: запросы и ответы. Порядок open важен: открытие
FIFO на чтение блокируется, пока нет писателя, и наоборот. Клиент сначала открывает
FIFO запросов на запись и отправляет запрос, и только потом открывает FIFO ответов на
чтение. Если открыть в другом порядке, клиент и сервер вечно ждут друг друга в open
(это взаимная блокировка, а не зависание программы). Клиент открывает FIFO запросов
с O_NONBLOCK, поэтому при незапущенном сервере сразу сообщает об этом.
Клиенты работают строго по очереди: FIFO ответов общий, и при одновременных клиентах
ответы перемешались бы. Для параллельных клиентов используются сокеты.

### Unix-сокеты
Сервер на каждое соединение запускает поток; клиенты - отдельные процессы (fork).
Каждый запрос обрабатывается 0.1 с (имитация работы); 5 клиентов по 3 запроса
завершаются примерно за 0.3 с, а при последовательной обработке потребовалось бы не
меньше 1.5 с. Это видно по общему времени и по одинаковым отметкам времени в логе сервера.
Сервер удаляет файл сокета при выходе.

### Безопасность вычислителя
Выражения разбираются через ast и допускают только числа, арифметику и скобки. eval
не используется: иначе клиент мог бы выполнить на сервере произвольный код. Слишком
большие степени отсекаются, плохой ввод не роняет сервер.

## Pipe: две типичные ошибки (pipe_demo.py)
- Запись в pipe без читателей: ядро посылает записывающему процессу SIGPIPE. В Python
  он по умолчанию игнорируется, поэтому приходит исключение BrokenPipeError (EPIPE); процесс
  с восстановленным SIG_DFL (как в C) убивается сигналом SIGPIPE.
- Если в родителе не закрыт конец записи, читающий процесс получает данные, но никогда
  не получает EOF: EOF приходит только когда закрыты ВСЕ копии конца записи.

## Разделяемая память без синхронизации (shm_sync_demo.py)
Писатель заполняет сегмент по частям, читатель в случайный момент забирает снимок. Без
синхронизации в большинстве прогонов читатель видит недописанные данные, причём число
недописанных кусков каждый раз разное - ошибка проявляется нерегулярно. С Event ("запись
закончена") неполных данных нет ни разу.

## Сравнение shared_memory и Pipe, сводная таблица (bench_ipc.py)
Передавался массив из 10^7 чисел float64 (80 МБ) в другой процесс. Время - от начала
отправки до момента, когда получатель имеет все данные; целостность проверена crc32.
Таблица ниже получена тем же прогоном, что и run_all_output.txt.

Выводы:
- Pipe (multiprocessing) оказался самым медленным. FIFO использует тот же буфер ядра, поэтому
  разницу объясняет надстройка multiprocessing: приём кусками и сборка сообщения в новый
  объект (вероятно, с дополнительным копированием).
- shared_memory с копированием в сегмент быстрее Pipe, но не мгновенна: копирование
  80 МБ в свежий сегмент, а выделение страниц стоит времени.
- Если данные сразу создаются в сегменте, передача занимает доли миллисекунды и не
  зависит от объёма: передаётся только имя сегмента. В этом преимущество разделяемой памяти.
- Цена - синхронизация: надо самому сообщить "данные готовы" (Event/семафор) и
  не допустить одновременной записи и чтения. Каналы и сокеты синхронизируют процессы
  сами (блокирующие read/write).
- Сегмент живёт в /dev/shm, пока его не удалят: создатель обязан вызвать unlink.
  Программы делают это в блоке finally; проверка ls /dev/shm после работы показывает,
  что остатков нет.

## Очистка
run_all.sh после работы проверяет: нет FIFO и сокета в /tmp, нет новых сегментов в
/dev/shm, нет очередей сообщений (ipcs -q; POSIX/SysV очереди не используются), нет
лишних процессов и зомби. Служебный процесс resource_tracker, который запускает
multiprocessing.shared_memory, завершается явно (stop_resource_tracker в common.py),
иначе после выхода он ненадолго остаётся зомби.

## Контрольные вопросы
1. **Почему разделяемая память - самый быстрый и самый опасный механизм IPC?**
   Быстрый: процессы отображают в свои адресные пространства одни и те же физические
   страницы, поэтому данные не копируются через ядро, и после настройки сегмента
   передача не требует системных вызовов - второй процесс просто читает ту же память.
   Опасный: ядро не следит за порядком доступа. Нет встроенной синхронизации (гонки,
   чтение недописанных данных - см. shm_sync_demo.py), нет границ сообщений, нет
   изоляции (ошибка одного процесса портит данные другого). Сегмент живёт в /dev/shm,
   пока его не удалят, и может "утечь" после аварийного завершения. Указатели внутри
   сегмента бессмысленны в другом адресном пространстве.
2. **Что произойдёт при записи в pipe, у которого закрыты все читающие концы?**
   Ядро пошлёт записывающему процессу сигнал SIGPIPE; по умолчанию он завершает процесс.
   Если сигнал игнорируется или перехвачен (в Python он игнорируется), write вернёт
   ошибку EPIPE (в Python - BrokenPipeError). Данные при этом не записываются. Это видно
   в pipe_demo.py, часть A. Обратная ситуация: чтение из pipe, у которого закрыты все
   записывающие концы, возвращает EOF (0 байт).

## Типичные ошибки (учтено)
- Лишние концы pipe закрываются в обоих процессах (в pipe_demo.py и в bench_ipc.py),
  поэтому читатель получает EOF.
- Порядок открытия FIFO подобран так, чтобы не возникала взаимная блокировка в open.
- Для разделяемой памяти используется Event; без него (shm_sync_demo.py) ошибки наблюдаются.
